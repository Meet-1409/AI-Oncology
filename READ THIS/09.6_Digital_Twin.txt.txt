09.6_Digital_Twin.txt

Project Name

AI Oncology Patient Intelligence Platform

Feature Name

Body (Digital Twin)

Document Purpose

This document defines the Body. It is the centrepiece of the platform and one of its primary navigation spaces. It provides an interactive 3D representation of the patient's anatomy and disease progression using validated patient data.

--------------------------------------------------

1. Purpose

The Body helps the oncologist understand the patient's disease visually.

It provides a clear representation of where the disease exists, how it has changed over time, and how it relates to the patient's anatomy.

The Body is a visualization tool and a navigation space. It does not generate medical information.

It must feel like a premium medical visualization tool.

--------------------------------------------------

2. Target User

Oncologist

--------------------------------------------------

3. Objectives

Display an interactive 3D human anatomy.

Display disease location.

Display disease severity.

Display disease progression.

Support historical comparison.

Synchronize with the patient's timeline.

Provide supporting evidence.

Act as a navigation space into related clinical information.

--------------------------------------------------

4. Spatial Composition

The Body sits at the centre of Patient Space and is present from the moment the oncologist arrives. It does not need to be opened.

Around it:

Patient identity and clinical context remain persistently visible.

The Journey is available as a continuous time control.

Supporting evidence is revealed in place when a site is selected.

Comparison controls appear only when comparison is active.

The interface around the Body must never distract from it. Chrome recedes; the anatomy leads.

--------------------------------------------------

5. 3D Anatomy

The model should represent:

Patient Body Structure

Skeleton

Major Organs

Affected Organs

Disease Locations

The model should not be an exact physical replica of the patient.

--------------------------------------------------

6. Patient Information

Display:

Patient Name

Patient ID

Age

Gender

Height

Weight

Current Diagnosis

Current Stage

Current Treatment

--------------------------------------------------

7. Disease Visualization

Disease should be displayed on the affected organs.

Severity should be represented using different shades of red.

Lighter shades represent lower severity.

Darker shades represent higher severity.

Healthy organs should remain visually distinguishable.

Severity color must never be the only indicator. A text label always accompanies it.

--------------------------------------------------

8. Interaction Controls

The oncologist should be able to:

Rotate the model.

Zoom the model.

Pan the model.

Reset camera.

Enter full screen mode.

Exit full screen mode.

Camera movement must never change the displayed medical information.

Every control has a keyboard equivalent.

--------------------------------------------------

9. Organ Interaction

Selecting an organ reveals, in place:

The clinical information for that organ

The supporting evidence for that organ

Related Journey events

Related Understanding

Selecting an organ is a navigation action. It never requires leaving the Body.

--------------------------------------------------

10. Timeline Integration

The Body synchronizes with the patient's timeline.

Selecting a timeline event updates the model to represent that point in time.

Moving through the Journey updates the Body continuously rather than in discrete jumps.

Every timeline update happens smoothly.

--------------------------------------------------

11. Comparison Mode

Allow comparison between two clinical dates.

Display:

Previous Digital Twin

Current Digital Twin

Visual disease progression

Comparison controls remain simple and easy to understand.

Entering and leaving comparison is a smooth spatial transition, not an abrupt layout change.

--------------------------------------------------

12. Disease Progression

The Body should visually represent:

Disease progression

Disease regression

Stable disease

Changes should be easy to identify. Motion draws attention to what changed between two clinical dates.

--------------------------------------------------

13. Evidence Panel

Every visualized disease location should provide supporting evidence.

Display:

Related Report

Report Date

Report Type

Evidence Source

Confidence

Users should be able to open the related report directly. The report opens in Focus above the Body.

--------------------------------------------------

14. AI Integration

The Body receives structured information from the backend.

The frontend is responsible only for visualization.

The Body must never generate medical information independently.

--------------------------------------------------

15. Navigation

The oncologist should be able to:

Open Timeline

Open Related Report

Open Patient Intelligence

Return to Patient Space

Continuous Return always moves one depth level out.

--------------------------------------------------

16. Motion

Loading reveals the anatomy progressively rather than displaying a blank area.

Movement between clinical dates is continuous.

Severity changes transition smoothly between shades rather than switching instantly.

Camera movement is damped and confident. No bouncing or elastic motion.

Reduced motion removes camera easing and severity transitions, presenting states directly. All clinical information remains identical.

--------------------------------------------------

17. User Actions

Rotate Model

Zoom Model

Pan Model

Reset Camera

Select Timeline Date

Compare Dates

Open Related Report

Open Patient Intelligence

--------------------------------------------------

18. Business Rules

Every patient has one Digital Twin.

The Digital Twin is generated from validated patient information.

Original reports remain the source of truth.

Disease visualization must always be supported by available evidence.

The Digital Twin must never display unsupported findings.

--------------------------------------------------

19. Empty States

No visualization available.

No supporting evidence available.

No comparison available.

Display informative messages for each situation.

--------------------------------------------------

20. Error States

Failed to load Digital Twin.

Missing visualization data.

Network error.

Rendering error.

Display clear recovery instructions.

A rendering failure must fall back to the non-3D equivalent rather than failing the space.

--------------------------------------------------

21. Performance Requirements

The Body should load efficiently and progressively.

Camera controls should remain smooth.

Model interaction should remain responsive.

Timeline transitions should remain smooth.

Comparison mode should not noticeably reduce performance.

Switching between patients should remain smooth.

Target 60 frames per second during all interaction.

Rendering complexity reduces automatically on low-capability devices without reducing clinical meaning.

--------------------------------------------------

22. Accessibility

Support keyboard shortcuts for every camera and selection action.

Provide a non-3D equivalent presenting every organ, severity and item of evidence available in the 3D view.

Maintain readable interface elements.

Provide descriptive labels for controls.

Maintain consistent spacing throughout the interface.

Respect reduced motion.

--------------------------------------------------

23. Completion Criteria

The Body is complete when:

The 3D model loads successfully.

Disease visualization is displayed.

Camera controls function correctly.

Timeline synchronization works.

Comparison mode functions correctly.

Organ selection reveals related clinical information.

Supporting evidence is accessible.

A non-3D equivalent is available.

Navigation integrates with the rest of the environment.

The module is ready for backend integration.
